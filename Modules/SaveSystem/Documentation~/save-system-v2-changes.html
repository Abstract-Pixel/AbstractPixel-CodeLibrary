Save System v2: what changed

Each part below shows the v1 code next to the v2 code. The parts you will use in almost every project come first. The internals come last.

How much of the plan is built

  • DoneStep 0. v1 tagged as save-system-v1, branches made.
  • DoneStep 1, safe storage. Atomic writes, backups, three save locations, working game profiles, tests.
  • DoneStep 2, the core. SaveSystem, restore after Awake and before Start, no SaveManager.
  • DoneSamples for steps 1 and 2. Six importable scenes, each with its own test.
  • Not startedSteps 3–8. [Save] fields, ISaveIn, SaveFiles.cs, ScriptableObject auto-registration, edit-time bridges, the editor window.

So scripts still pick their save file with [Savable(SaveCategory.X)] and implement ISavable<T>. The level 1 style from the design page ([Save] int current;) comes in step 3. Tests: 103 EditMode and 10 PlayMode, all passing.

Saving a MonoBehaviour

every saved script

The script itself looks the same. What changed is when the saved value arrives. v1 restored data at the end of the frame after a scene group finished loading, so Start still saw new-game values and the UI had to wait for a load event. v2 restores right after every Awake and before any Start.

Beforev1
[Savable(SaveCategory.Game)]
public class Health : MonoBehaviour, ISavable<int>
{
    public int Current;

    void Start()
    {
        Current = 100;
        // Saved data hasn't arrived yet here.
        // It comes at the end of the frame after the
        // scene group transition, from SaveManager.
    }

    public int CaptureData() => Current;
    public void RestoreData(int data) => Current = data;
}

// A health bar had to wait for the load event:
void OnEnable() =>
    SaveEventBus.OnLoadCategoryCompleted += c => Refresh();
Afterv2
[Savable(SaveCategory.Game)]
public class Health : MonoBehaviour, ISavable<int>
{
    public int Current { get; private set; }

    // New-game values go in Awake.
    void Awake() { Current = 100; }

    public int CaptureData() => Current;
    public void RestoreData(int data) => Current = data;
}

// A health bar can read the saved value in Start:
void Start()
{
    shownHealth = health.Current;   // already restored
}
The one rule to remember: set new-game values in Awake. A saved field assigned in Start overwrites the value that was just restored.
  • The Savable Bridge is still the component that connects the script. The editor still adds it.
  • The bridge now runs first ([DefaultExecutionOrder(-10000)]) and registers in Start. That is what puts restore between Awake and Start.
  • An object spawned later, or one disabled and enabled again, gets its data back the same way. In v1 anything that appeared after the single load never got data.
  • A chest in an additive scene saves into its own scene's file, not the active scene's.

Saving, and why there is no Load

every game

SaveActions is now SaveSystem. Loading is no longer a call you make. An object gets its data as soon as both the object and its data exist, whichever comes second.

Beforev1
SaveActions.SaveAll();
SaveActions.SaveDataOf(SaveCategory.Settings);
SaveActions.SaveDataOfScope(SaveScope.Global);

SaveActions.LoadAll();
SaveActions.LoadDataOf(SaveCategory.Settings);

// No SaveManager in the scene? SaveActions created
// one with no config, and it threw in Awake.
Afterv2
SaveSystem.SaveAll();
SaveSystem.Save("Settings");   // one save file

// No load calls. Registering restores when the data
// is ready; opening a game profile restores everything
// registered before it.

// No config? One clear error at startup, and every
// SaveSystem call is a safe no-op.
  • SaveAll writes only the save files that changed. An unchanged file isn't rewritten.
  • Saving no longer erases objects that aren't loaded right now. v1 rebuilt each file from the registered objects only, so a boss in an unloaded scene lost its data. v2 keeps the data it read and merges new captures into it.
  • When a saved object goes away, its latest values are captured first, so they're written on the next save.
  • MonoSaveActions (for UnityEvents) keeps SaveAll() and has Save(string). Its load methods are gone.

Setting it up in a project

once per project

Nothing goes in a scene any more. The save system starts by itself before the first scene loads.

Beforev1
1. Put a SaveManager in the boot scene.
2. Drag a SaveSystemConfigSO onto it.
3. Set up SceneCoordinator scene groups, because
   loading waited for a scene group transition.
4. Tune script execution order so the SaveManager
   ran before other scripts.
Afterv2
1. Create a SaveSystemConfigSO
   (Assets > Create > Utility > SaveSystemConfigSO).
2. Name it SaveSystemConfig.
3. Put it in a folder named Resources.

That's all. SaveStartup reads it before the first
scene, opens a game profile if the policy says so,
and resets itself every time play mode starts.

The config inspector changed in four places:

Fieldv1v2
Each category's placeDirectoryScope: Global or GameProfileLocation: Global, GameProfile or Scene (old values carry over)
Scene-specific checkboxIsSceneSpecificRemoved; pick Scene as the location
AutosaveNoneSaveOnQuit and SaveOnFocusLoss, both off by default
Use Debug PathSaved into Assets/DebugSaveFiles, which Unity imported as assetsSaves into <project>/DebugSaveFiles, next to Assets

StartupPolicy works as before: AutoSetUp reopens the last game profile or creates "Game Profile 1"; Manual waits for your save slot screen.

The Resources location is temporary until the config-location decision (GitHub #18) is settled.

Choosing where data lives

most games

There are exactly three save locations. Scene used to be a checkbox on a GameProfile category. Now it is a location of its own, and it always sits inside a game profile.

Beforev1
public enum SaveScope
{
    None = 0,
    Global = 1,
    GameProfile = 2
}

// Scene data: a GameProfile category with
// IsSceneSpecific ticked. Its folder name came from
// SceneActions.ActiveSceneGroup.MainScene.
Afterv2
public enum SaveLocation
{
    Global = 1,       // settings, shared by every game profile
    GameProfile = 2,  // one playthrough
    Scene = 3         // one scene in one playthrough
}

// The script only names its save file. The config
// says which location that file lives in:
[Savable(SaveCategory.Position)]  // Position → Scene
public class Chest : MonoBehaviour, ISavable<bool> { … }

Switching game profiles keeps Global data and swaps everything else. See sample 04 Save Locations.

Game profiles and save slots

most games

You reach game profiles through SaveSystem.GameProfiles. The v1 methods mixed creating and opening, and two of them didn't work.

Beforev1
SaveProfileManager profiles =
    SaveManager.Instance.ProfileManager;

profiles.CreateNewActiveProfileDirectory(); // create + open
profiles.SetCurrentActiveProfile(id);       // "last opened"
                                            // wasn't saved
string[] ids = profiles.GetAllProfileIds(); // always empty
profiles.DeleteProfileDirectory(id);        // missed the
                                            // folder
GameProfileManifest m = profiles.LoadProfileManifestByID(id);
// m.ProfileName, m.CreationDateAndTime, m.LastSavedScene
Afterv2
SaveProfileManager profiles = SaveSystem.GameProfiles;

string id = profiles.CreateNew("Game Profile 2"); // create only
profiles.Open(id);       // remembered for the next launch
SceneManager.LoadScene(SceneManager.GetActiveScene().name);

foreach (GameProfileManifest slot in profiles.GetAll())
{
    Debug.Log($"{slot.DisplayName}  {slot.LastSavedUtc}  " +
              $"{slot.PlaytimeSeconds}s  {slot.LastScene}");
}

profiles.Delete(id);     // every file of that game profile
bool isOpen = SaveSystem.IsGameProfileOpen;
  • SaveAll keeps the open game profile's manifest current: last saved time, last scene and playtime.
  • The manifest has a Custom dictionary for game-specific slot details, such as difficulty or chapter.
  • After opening a different game profile, reload your scenes. An object registered under the previous game profile never writes its values into the new one. It only moves over if the new game profile has data for it.

Saving a plain C# class

often

This is new. In v1 only MonoBehaviours with a Savable Bridge could save. In v2 any object can register itself with one line.

Beforev1
// Not possible. Every saved script had to sit on a
// GameObject with a Savable Bridge, so data classes
// were wrapped in a MonoBehaviour just to be saved.
Afterv2
[Savable(SaveCategory.Game)]
public class Inventory : ISavable<InventoryData>
{
    public List<string> Items { get; private set; }

    public Inventory()
    {
        Items = new List<string> { "Wooden Sword" };
        // Last line: saved items may be restored here.
        SaveSystem.Register(this, "player-inventory");
    }

    public InventoryData CaptureData() =>
        new InventoryData { Items = new List<string>(Items) };
    public void RestoreData(InventoryData data) =>
        Items = new List<string>(data.Items);
}

// Whoever owns it unregisters it when its scene ends:
void OnDestroy() => SaveSystem.Unregister(inventory);

A plain class has no GameObject to carry a save ID, so you pick the ID yourself. It must be unique within its save file.

Reacting to save events

sometimes

v1 had nine events for loads and saves by category and scope. Because restore is automatic, v2 keeps the two that still mean something.

Beforev1
SaveEventBus.OnSaveAllCompleted += OnSaved;
SaveEventBus.OnSaveCategoryCompleted += c => { };
SaveEventBus.OnSaveScopeCompleted += s => { };
SaveEventBus.OnLoadAllCompleted += OnLoaded;
SaveEventBus.OnLoadCategoryCompleted += c => { };
SaveEventBus.OnLoadScopeCompleted += s => { };
Afterv2
SaveSystem.Saved += OnSaved;   // after SaveAll or Save

SaveSystem.GameProfileOpened += id =>
{
    // Subscribing while a game profile is already open
    // calls this right away. AutoSetUp opens one before
    // any Awake runs, so late subscribers still hear it.
};

// The same events also live on SaveEvents.

Forgetting saved data on purpose

sometimes

This is new. It removes one saved object's data from its save file, for something like a coin that was picked up and should stay gone.

New in v2SaveSystem.Forget
SaveSystem.Forget("Game", "quest-dragon");   // save file name, save ID
SaveSystem.SaveAll();                        // the entry is gone from the file

// If that object is still registered, it is dropped too,
// so destroying it afterwards can't write it back.
For objects with a Savable Bridge, the save ID is <bridge GUID>/<script GUID>, and game code can't read it easily yet. Step 3 adds SetSaveId and spawned copies, which make this practical for scene objects.

Saving a ScriptableObject

sometimes

This is new, done by hand for now. An asset registers itself the same way a plain class does. Step 5 makes it automatic.

New in v2until step 5
[Savable(SaveCategory.Achievements)]
public class GameProgress : ScriptableObject, ISavable<GameProgressData>
{
    public int LevelsCompleted;

    void OnEnable()  => RegisterWithSaveSystem();
    void OnDisable() => SaveSystem.Unregister(this);

    // In the Editor the asset can load before play mode starts the save system,
    // so a scene script calls this again in Awake. Registering twice is harmless.
    public void RegisterWithSaveSystem() => SaveSystem.Register(this, "game-progress");

    public GameProgressData CaptureData() => new GameProgressData { LevelsCompleted = LevelsCompleted };
    public void RestoreData(GameProgressData data) => LevelsCompleted = data.LevelsCompleted;
}

Editor tools

while debugging

The SaveManager inspector is gone along with SaveManager. Everything now lives in one menu.

Beforev1
SaveManager inspector, Debug Controls:
  Delete All Saves          (no confirmation)
  Open Release / Debug Save Directory
  SAVE ALL DATA ! / LOAD ALL DATA !

Tools > External Project Tools > Save System:
  Open Release Folder, Open Debug Folder
  Delete All Save Files     (deleted nothing:
                             its paths were never set)
Afterv2
Tools > External Project Tools > Save System:
  Save All                  (play mode only)
  Load All                  (play mode only: re-reads every
                             file, restores every object)
  Open Release Folder
  Open Debug Folder
  Delete All Save Files     (asks first, uses the same
                             folders the game writes to)

What's on disk

while debugging

Folders are shorter. Every file has a backup. Writes go to a temp file first, so a crash mid-write can't destroy the last good save.

Beforev1 folders
SaveFiles/
  Global/
    Settings.json
    SystemMetaData.json
  GameSaves/SaveProfiles/
    GameProfilea1b2c3/
      GameProfileManifest.json
      Profile.json
      Forest/            ← scene-specific category
        Chests.json
Afterv2 folders
SaveFiles/                 (DebugSaveFiles/ when debugging)
  Global/
    Settings.json
    Settings.backup.json   ← last good version
    SaveSystemMetaData.json
  GameProfiles/
    a1b2c3/
      GameProfileManifest.json
      GameProfile.json
      Scenes/
        Forest/
          Scene.json
Beforev1 file
{
  "Version": "1.0",
  "Timestamp": "2026-07-05T17:09:54.0000000Z",
  "ProfileID": "a1b2c3",
  "DataMap": {
    "Player GameObject #[5eecb91f-…]": {
      "Health Component #27062df3-…": 40
    }
  }
}
Afterv2 file
{
  "FormatVersion": 2,
  "Version": "1.0",
  "Timestamp": "2026-11-13T04:12:08.0000000Z",
  "ProfileID": "a1b2c3",
  "FileName": "GameProfile",
  "Entries": {
    "5eecb91f-…/27062df3-…": {
      "name": "Assets/Scenes/Level.unity/Player/Health",
      "data": 40
    }
  }
}
  • Entries are keyed by save ID only. name is just there to help a human reading the file.
  • FormatVersion lets a later version spot and upgrade older files. A different version logs a warning.
  • If a file is corrupt, the backup loads with a warning that names the file. If both are unreadable, you get one error that says what to do.
  • v2 doesn't read v1 save files. The shipped game stays on save-system-v1.

Storage parts under the hood

library work and tests

You only need these to extend the save system or write tests for it. v1 passed full file paths around through static classes. v2 uses small parts, each with one job, that work with keys like GameProfiles/a1b2c3/GameProfile.

Beforev1
SavePathGenerator.Initialize(config);         // static
string path = SavePathGenerator.GetPath(definition, profileId);

var storage = new FileDataStorageService();
storage.SaveFile(json, path);
// Deleted the old file, then moved the new one in.
// A crash in between left no save at all.

string text = storage.LoadFile(path);
Afterv2
IDataStorageService storage =
    new DiskStorageService(useDebugFolder: true, FileExtension.json);
// Tests use: new MemoryStorageService()

var paths = new SavePathGenerator();          // builds every key
string key = paths.GetSaveFileKey(
    "GameProfile", SaveLocation.GameProfile, gameProfileId, null);

var store = new SaveFileStore(storage, new JsonSerializer());
store.Write(key, saveFile);    // keeps the last good one as .backup
store.TryRead(key, out SaveFileData loaded); // falls back to it
PartIts one job
IDataStorageServiceWrite, read, list and delete text by key. A write fully succeeds or leaves the old text untouched.
DiskStorageServiceKeys become files: write .tmp, flush, then File.Replace. It retries if Windows briefly locks the file.
MemoryStorageServiceA dictionary, so tests never touch real save files.
SavePathGeneratorBuilds every key in one place, so save and load can't disagree.
SaveFileStoreBackups, and reads with a fallback to them.
SaveProfileManagerGame profiles: create, open, list, delete, and remember the last one opened.
SaveRegistry, LoadedSaveData, SaveSessionWhich objects are registered, the data read from disk, and the wiring that applies the whichever-second rule.

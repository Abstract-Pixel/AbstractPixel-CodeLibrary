Code map

Every script under Runtime and Editor, grouped by folder: its job, its file path, and when you'd touch it yourself.

A saved object is anything whose data the save system captures and restores: a MonoBehaviour, a plain C# class or a ScriptableObject.

A saved script is a MonoBehaviour with saved fields or ISavable. Each saved script on a GameObject is its own saved object with its own save ID, and the GameObject's Savable Bridge connects them all. A GameObject can hold any number of saved scripts, including two of the same script.

How the parts fit together#

Runtime/PublicAPI the daily API#

What game code calls and implements. Open a row below for the full story, or follow its "Full reference" link for the type's own page.

  • SaveActions static class The class game code calls to save, reload, forget and manage game profiles. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveActions.cs

    Every game that uses this save system calls into SaveActions: it's the one class your game code talks to for saving, reloading a file, forgetting an object, and registering plain classes. If you're writing gameplay code that needs to trigger a save or read back data, this is the entry point you reach for.

    Full reference →

  • SaveAttribute attribute [Save]: marks a field to save and restore by name. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveAttribute.cs

    Put [Save] directly on any field you want captured and restored automatically — a health value, an inventory list, a position you track by hand. This is the first thing to reach for whenever a MonoBehaviour's field needs to survive a save and reload; most saved data in a typical game goes through this attribute rather than a custom ISavable implementation.

    Full reference →

  • SaveIdAttribute attribute [SaveId]: keeps a registered class's save ID stable after a rename. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveIdAttribute.cs

    Use [SaveId] the moment you rename a plain C# class (not a MonoBehaviour) that registers itself with SaveActions, so existing save files keep matching it by its old name instead of losing their data. Skip it for scene scripts — SavableBridge already gives those a stable ID — this is specifically for classes that register themselves in code.

    Full reference →

  • ISavable interface A saved object that captures and restores its own data instead of using [Save]. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/ISavable.cs

    Implement ISavable<TData> when your object's data can't just be captured as a flat set of [Save] fields — it needs computing on the way out, converting on the way in, or it holds something JSON can't store directly, such as a runtime-only reference. Reach for it instead of [Save] whenever the shape of what you save has to differ from the shape the object actually keeps in memory.

    Full reference →

  • ISaveIn interface Picks the save file for a registered class's [Save] data. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/ISaveIn.cs

    Implement ISaveIn<TFile> on any plain class or ISavable object whose data shouldn't go in the default GameProfile file — for example persistent unlocks that belong in a Settings-like file, or scene-scoped data. Without it, a registered plain class's data lands in the GameProfile file by default; add this interface the moment you need it somewhere else.

    Full reference →

  • IOnRestored interface Runs code right after each restore. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/IOnRestored.cs

    Implement IOnRestored on a saved object when something needs to happen right after its data comes back — reapplying a buff, refreshing a UI element, re-subscribing to an event now that real values are in place. It fires after every restore, including the very first one when new-game values are set, so use it for setup that depends on final values rather than constructor-time defaults.

    Full reference →

  • ISaveFile interface Marks a save file class, such as SaveFiles.Settings. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/ISaveFile.cs

    Implement this marker interface on a class whenever you need a type-safe way to refer to a save file in code — as the generic argument to SaveActions.Save<TFile>(), SaveStorage, or ISaveIn<TFile> — instead of passing the file's name as a loosely-typed string. The built-in SaveFiles nested classes already implement it; add your own only if a library module defines an extra save file.

    Full reference →

  • SaveFiles static class The five built-in save files: GameProfile, Scene, Settings, Input, Achievements. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveFiles.cs

    Use the five nested classes under SaveFiles (GameProfile, Scene, Settings, Input, Achievements) wherever a type argument or file reference is expected, such as SaveActions.Save<SaveFiles.Settings>(). Every game that uses more than the single default save file reaches for these constantly.

    Full reference →

  • SaveFileDefaultsAttribute attribute [SaveFileDefaults]: gives a library module's save file class a starting config row. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveFileDefaultsAttribute.cs

    Put [SaveFileDefaults] on a save file class you're shipping as part of a reusable library module, so the save system config automatically gets a starting row for it the first time a project imports the module, instead of making every consumer add the row by hand.

    Full reference →

  • SaveFileReference struct A save file picked in the Inspector from a dropdown of the config's save file list. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveFileReference.cs

    Use a SaveFileReference field on a MonoBehaviour or ScriptableObject when you want a designer to pick a save file from a dropdown in the Inspector, rather than hard-coding a SaveFiles.X type argument in code — handy for tools and debug buttons that should work against whichever file someone selects.

    Full reference →

  • SaveEventBus static class The load and save events, including the sticky load events. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveEventBus.cs

    Subscribe to SaveEventBus's static events whenever code elsewhere in the game needs to react to a load or save happening — showing a save icon, refreshing a screen after a game profile opens, logging a failed save. Every load event is sticky, so subscribing after the event already fired still calls your handler once, right away.

    Full reference →

  • SaveStorage static class Reads and writes a whole save file as JSON text directly. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveStorage.cs

    Call SaveStorage directly when you need the raw JSON text of a whole save file — for an editor tool, a debug button that dumps a file's contents, or a migration script — rather than going through the normal register/capture/restore flow. Most gameplay code never touches this; SaveActions is the everyday entry point instead.

    Full reference →

  • SavedScriptExtensions static class SetSaveId: gives a spawned copy its own save ID. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SavedScriptExtensions.cs

    Call the SetSaveId extension method right after Instantiate-ing a prefab that has saved scripts on it, so the spawned copy gets its own distinct save ID instead of colliding with the original or with other copies. Needed any time your game spawns more than one instance of the same saved prefab at runtime.

    Full reference →

  • SaveTransform component Saves this GameObject's position, rotation and local scale, with no code. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveTransform.cs

    Add this component to a level object whose position, rotation or scale should be exactly where the player left it after a reload — a pushed crate, a moved platform, anything that can end up somewhere other than its starting Transform. No code required: just add the component.

    Full reference →

  • SaveActiveState component Saves whether this GameObject is active, with no code. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveActiveState.cs

    Add this component to a GameObject you turn on and off at runtime — a cleared trap, an opened gate, a collected pickup hidden instead of destroyed — so its active/inactive state survives a reload without writing any save code yourself.

    Full reference →

  • SaveDestroyed component Forgets this GameObject, then destroys it, so it stays gone after a reload. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/SaveDestroyed.cs

    Add this component to a scene object you expect the player to permanently destroy — a chest they loot and discard, an obstacle they clear — then call its DestroyAndForget method instead of Unity's Destroy, so the object writes a gone marker and stays gone after a reload instead of reappearing.

    Full reference →

  • MonoSaveActions component Saving, loading and game profiles from buttons and UnityEvents, with no code. Abstract Pixel Library/Modules/SaveSystem/Runtime/PublicAPI/MonoSaveActions.cs

    Add this component when a designer needs to wire Save, Reload or game-profile actions straight from the Inspector — a UnityEvent on a UI Button, for instance — without writing a script that calls SaveActions directly. Common on save-slot screens and debug menus built by someone who isn't touching code.

    Full reference →

Runtime/SavedObjects#

Connects the scripts on a GameObject to the save system.

  • SavableBridge component Connects a GameObject's saved scripts to the save system. Abstract Pixel Library/Modules/SaveSystem/Runtime/SavedObjects/SavableBridge.cs

    You won't usually add this yourself — the editor adds a Savable Bridge automatically the moment a GameObject gains a saved script. Look at it directly when you need the GameObject's save ID at runtime, or when debugging why a scene object's data isn't being found.

    Full reference →

  • SavableBridgeIdentity static class Decides when a bridge needs a new GUID: a blank one, or a copy of another bridge. Abstract Pixel Library/Modules/SaveSystem/Runtime/SavedObjects/SavableBridgeIdentity.cs

    Internal: decides whether a Savable Bridge needs a brand-new GUID (a blank bridge, freshly added) or should copy another bridge's identity (duplicating a prefab instance in the editor). You'd only read this while debugging why two copies of the same object ended up sharing — or not sharing — a save ID.

  • SavableIdentification class One saved script's class name and GUID, as the bridge stores them. Abstract Pixel Library/Modules/SaveSystem/Runtime/SavedObjects/SavableIdentification.cs

    Internal: the exact pair of values — class name and GUID — that a Savable Bridge stores on disk, in the scene file, to identify one saved script. Relevant only if you're debugging a scene file's serialized bridge data or extending how bridges identify saved scripts.

  • SavableTarget class One saved script found on a GameObject: its reflection data or its [Save] field set. Abstract Pixel Library/Modules/SaveSystem/Runtime/SavedObjects/SavableTarget.cs

    Internal: represents one saved script the bridge found on its GameObject, holding either its reflected [Save] field set or a reference to its ISavable implementation. You'd look here when tracing exactly what data the save system thinks a particular script exposes.

  • SavedScript static class Whether a script class saves, and which save file its data goes in. Abstract Pixel Library/Modules/SaveSystem/Runtime/SavedObjects/SavedScript.cs

    Internal: a quick classification of one script class — does it save at all, and if so, which save file does its data belong in. The bridge and the registry both consult this before doing any real work, so it's a good starting point when debugging why a script isn't being treated as saved.

  • SavedFieldSet class Every [Save] field on a class, captured to JSON and restored back. Abstract Pixel Library/Modules/SaveSystem/Runtime/SavedObjects/SavedFieldSet.cs

    Internal: holds every [Save] field found on one class, and does the actual work of capturing them to JSON and writing them back on restore. This is the machinery behind the [Save] attribute; read it to understand exactly how field capture and restore work, not to call it directly.

  • SavedFieldRules static class The mistakes a [Save] field or a saved class can make, and their fixes. Abstract Pixel Library/Modules/SaveSystem/Runtime/SavedObjects/SavedFieldRules.cs

    Internal: the catalog of mistakes a [Save] field or a saved class can make — an unsupported type, a missing save ID, and so on — along with the fix text shown in the editor. Look here to see the exact wording of a warning, or to add a new mistake check.

Runtime/Core#

The running save system: the registry of saved objects, the loaded data, and the timing rules.

  • SaveSession class One running save system: wires the registry, loaded data and game profiles together. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveSession.cs

    Internal: the one object that exists while the save system is running, wiring together the registry, the loaded data and the open game profile. SaveActions forwards almost every call straight to the current session. Read this to understand how the save system starts up and holds its running state together, not to call it from game code.

  • SaveStartup static class Starts the save system before the first scene loads, and resets it when play mode starts and stops. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveStartup.cs

    Internal: boots the save system before the first scene loads, and resets everything when Play mode starts and stops in the editor. Relevant if you're debugging startup order, or figuring out why state did or didn't reset between Play sessions.

  • SaveRegistry class Every registered saved object, stored by save file name and save ID. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveRegistry.cs

    Internal: the live table of every registered saved object, keyed by which save file it belongs to and its save ID. This is what SaveActions.Register/Unregister actually update; read it when debugging whether a particular object is registered at all.

  • SavedObjectEntry class One registered saved object: its owner, where its data lives, and how to capture and restore it. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SavedObjectEntry.cs

    Internal: one row in the registry — a registered object's owner reference, which save file its data lives in, and the capture/restore functions to call on it. Worth reading if you need to see exactly what the registry remembers about a single saved object.

  • SavedObjectTracker class Captures, restores and forgets registered saved objects, following the whichever-second rule. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SavedObjectTracker.cs

    Internal: does the actual capturing, restoring and forgetting of every registered object, applying the "whichever comes second" rule — an object gets its data as soon as both the object and its data exist. Read this to understand the exact timing of when capture/restore happens relative to registration.

  • LoadedSaveData class The saved data read from disk, kept in memory by key and save ID; also calls IOnRestored. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/LoadedSaveData.cs

    Internal: the save data that's been read from disk, kept in memory keyed by save file and save ID, and the thing that actually calls IOnRestored once it hands data back to an object. Relevant when debugging what's currently loaded versus what's on disk.

  • LoadEventLog class Remembers which save files have loaded, so a late subscriber's load event still fires (sticky). Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/LoadEventLog.cs

    Internal: remembers which save files have already fired their load event this session, so that a script subscribing late to SaveEventBus still gets called immediately instead of missing the event. Read this if a sticky load event isn't firing when you expect.

  • SaveSessionEvents class Reads save files on startup and raises the load and save events on SaveEventBus. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveSessionEvents.cs

    Internal: reads every save file on startup and raises the corresponding load (and later, save) events on SaveEventBus. This is the piece that actually fires the events other code subscribes to — read it to trace exactly when and why an event fires.

  • SaveFileLookup class Finds the config's save file list row for a save file class. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveFileLookup.cs

    Internal: given a save file class, finds its matching row in the config's save file list. Used internally whenever the save system needs to turn a SaveFiles.X type into its configured location and backup setting.

  • SaveFileAddress struct Where one save file lives: its storage key and whether it keeps a backup. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveFileAddress.cs

    Internal: a small value — a storage key plus whether that file keeps a backup — describing exactly where one save file lives right now. Built fresh whenever the open game profile or scene changes, since both can shift where a file's data actually is.

  • SaveFileAddresses class Works out every save file's address right now, which depends on the open game profile and scene. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveFileAddresses.cs

    Internal: works out every save file's current address in one place, since the right answer depends on which game profile is open and which scene is loaded. Read this when tracing exactly which physical file a given save file class currently maps to.

  • SaveFileClassFinder class Finds the save file class a config row stands for. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveFileClassFinder.cs

    Internal: given a config row, finds the actual save file class it stands for — reversing what SaveFileLookup does. Used when the save system needs to go from configuration data back to a concrete type.

  • AutomaticSaveIds class Gives a plain registered class with no save ID one of its own: its class name, then "Name 2", "Name 3". Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/AutomaticSaveIds.cs

    Internal: when a plain registered class has no explicit save ID, this gives it one automatically — its class name, then "Name 2", "Name 3" for further live instances in the order they register. Read this if you're seeing unexpected automatic save IDs and want to know exactly how they're assigned.

  • LowestFreeNumber static class Numbers that start at 1 and are reused, for slot numbers and automatic save IDs. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/LowestFreeNumber.cs

    Internal: a small utility that hands out numbers starting at 1 and reuses ones that are freed, used both for save slot numbers and for the "Name 2", "Name 3" automatic save ID numbering. Not specific to saving conceptually — just counting logic two features share.

  • AutosaveTicker component A hidden object that calls SaveActions.SaveAll on the config's autosave interval. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/AutosaveTicker.cs

    Internal: a hidden runtime object that calls SaveActions.SaveAll on a timer, at the interval configured on the save system config asset. Look here if autosave isn't firing on the interval you expect, or to see exactly how the timer is implemented.

  • SaveLog static class Every Console message the save system writes goes through here; tests can expect a message instead of printing it. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveLog.cs

    Internal: every Console message the save system itself writes goes through this one choke point, so tests can assert a specific message was logged instead of needing to capture real Console output. Not something game code calls directly.

  • SaveSystemHelpAttribute attribute The base attribute behind every inspector's "?" button. Abstract Pixel Library/Modules/SaveSystem/Runtime/Core/SaveSystemHelpAttribute.cs

    Internal: the base attribute behind every inspector's "?" help button — put it on an Editor or Inspector class to give it a button that opens a specific guide page. See Debug and inspect for how the resulting buttons look in practice.

Runtime/Storage#

Reads and writes save files safely, with backups.

  • IDataStorageService interface Stores text under string keys. The storage service decides where it really goes. Abstract Pixel Library/Modules/SaveSystem/Runtime/Storage/IDataStorageService.cs

    Internal: the abstraction every storage backend implements — store this text under this string key — leaving the decision of where it really ends up (disk, memory, something else) to whichever implementation is plugged in. Implement this yourself only if you're adding a wholly new storage backend.

  • DiskStorageService class Writes keys as files on disk, through a temporary file so a crash mid-write can't destroy a save. Abstract Pixel Library/Modules/SaveSystem/Runtime/Storage/DiskStorageService.cs

    Internal: the real, on-disk implementation of IDataStorageService every game actually ships with — it writes through a temporary file first, so a crash or power loss mid-write can't corrupt or destroy an existing save. You won't call this directly; it's wired in automatically.

  • MemoryStorageService class Keeps keys in memory instead of on disk. Abstract Pixel Library/Modules/SaveSystem/Runtime/Storage/MemoryStorageService.cs

    Internal: an in-memory stand-in for IDataStorageService that never touches the disk at all. Swapped in by the test suite specifically so tests can save and load freely without ever creating or corrupting a real save file on the machine running them.

  • SaveFileStore class Reads and writes one key safely: every write backs up the previous good copy first. Abstract Pixel Library/Modules/SaveSystem/Runtime/Storage/SaveFileStore.cs

    Internal: reads and writes one storage key safely — every write first backs up whatever was there before, so a failed or interrupted write can't leave you with neither the old data nor the new. Sits directly on top of whichever IDataStorageService is active.

  • SaveFileAccess class Reads and writes a whole save file as text for one config and one storage. Abstract Pixel Library/Modules/SaveSystem/Runtime/Storage/SaveFileAccess.cs

    Internal: reads and writes an entire save file as text, for one specific config and one specific storage backend. SaveStorage is the public-facing wrapper around this that game code and editor tools actually call; read this only if you need the lower-level mechanics.

  • SaveFileTarget struct Which copy of a save file a SaveStorage call means: this game profile, another one, or a scene. Abstract Pixel Library/Modules/SaveSystem/Runtime/Storage/SaveFileTarget.cs

    Internal: pins down exactly which physical copy of a save file a SaveStorage call means — this game profile's copy, a different named one, or a particular scene's copy — since the same save file class can resolve to different files depending on context.

  • SavePathGenerator static class Builds every storage key the save system uses, so saving and loading never disagree. Abstract Pixel Library/Modules/SaveSystem/Runtime/Storage/SavePathGenerator.cs

    Internal: the single place that builds every storage key the save system uses, so that the code saving a file and the code loading it always agree on exactly where it lives. Read this if you're tracking down a mismatch between where something was written and where it's being looked for.

  • StorageKey static class Checks that a storage key is safe to turn into a file name. Abstract Pixel Library/Modules/SaveSystem/Runtime/Storage/StorageKey.cs

    Internal: validates that a storage key is safe to turn directly into a file name on disk, rejecting characters a filesystem can't handle. A small guard rail the rest of the storage layer relies on.

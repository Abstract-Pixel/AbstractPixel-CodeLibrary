Implement ISavable<TData> when the saved shape differs from the live fields, the data needs a copy or a conversion on the way in and out, or the fields hold things JSON can't store. A class uses [Save] fields or ISavable, never both.

CaptureData hands the save system a copy, so later changes to Items never reach data that was already captured. RestoreData puts the saved items back. Register on the last line, since saved data may arrive inside that call.

Show the resultThe Saved Objects window lists "player-inventory" under the GameProfile file, and the file on disk holds InventoryData's shape, not Inventory's: 
"player-inventory": { "Items": ["Wooden Sword", "Potion"] }

Inventory, Inventory 2, Inventory 3#

A plain class or ISavable object with no custom save ID uses its class name. A second live instance of the same class gets "Inventory 2", then "Inventory 3", in the order they register.

The Saved Objects window shows all three as separate cards: Inventory, Inventory 2 and Inventory 3, each with its own Items. If the order these register in can change between runs, the numbers would swap data between them.

Give each one a custom save ID when registration order isn't fixed: SaveActions.Register(this, $"inventory-{owner.name}").
If it goes wrong
Two instances swap data after a code change
Their registration order changed, so the numbering changed with it. Give each a custom save ID.
"can't register... another object already uses save ID" in the Console
Two live objects already share an explicit save ID. Make the custom ID unique per instance.

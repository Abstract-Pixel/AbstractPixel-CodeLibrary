Save, restore and react to data 1 daily code

Set up the config once, then put [Save] on the fields you want to keep.

Which way to save #

Most saved objects just need [Save] fields. Reach for the others only when they solve a real problem below.

WayUse it when
[Save] fieldsThe default. Your data is already plain fields: numbers, Vector3, lists, or your own [Serializable] classes.
[Save] fields + ISaveIn<TFile>Same as above, but this data belongs in a specific file, not the default GameProfile one: a Global setting, or a Scene file. See Choose where data goes.
IOnRestoredYou need to run code right after this object's data comes back, such as pushing a loaded value onto a Transform. Add it alongside [Save] fields or ISavable; it doesn't hold data on its own.
ISavable<TData>Your data isn't plain fields: it needs converting on the way in or out, or holds something JSON can't store. See Saving complex data with ISavable.

Set up a project 0 no code#

In the Unity menu, choose Tools > External Project Tools > Save System > Create Config. Nothing goes in a scene.

Show the resultThe menu item creates Assets/Resources/SaveSystemConfig.asset, shown in the SaveSystemConfigSO inspector. The save system reads it before the first scene loads.
With no config, the save system logs one error naming the menu item. Save calls do nothing, and the game keeps running.
If it goes wrong
"Can't find the save system config" in the Console
Run Create Config. The error names the exact menu path.
Two configs after a merge
Delete the one you don't want. Only the asset at Assets/Resources/SaveSystemConfig.asset is read.

Save a field on a script 1 daily code#

Try it in the sample
Open sample 01: Save A Field →

Sample 01 · Save A Field

  1. Open the Save A Field scene and press Play.
  2. Press Take 10 damage and Find an item a few times, then press Save.
  3. Press Reload scene.

Put [Save] on each field you want to keep. Public, private and inherited fields all work, on numbers, text, bools, enums, and the types below.

Saved fields also work on arrays, Color, Rect, and any [Serializable] class. The editor adds a Savable Bridge to the GameObject, which connects every saved script on it to the save system.

Don't reset a saved field in Start. The save system restores saved data after every Awake and before any Start, so resetting it in Start overwrites the value just loaded. Set new-game values in the field's initializer or in Awake instead.
Show the resultAfter Play, the Savable Bridge's inspector lists Health and its save ID. The saved JSON holds a field named "current", not "Health" or "100" alone: 
{ "current": 70, "lastCheckpoint": { "x": 2, "y": 0, "z": -4 } }
If it goes wrong
The field keeps its new-game value after Reload scene
Something in Start or OnEnable is setting the field back to its new-game value, after the save system already restored the loaded one there. Move that assignment to the field's initializer or to Awake.
No Savable Bridge appears on the GameObject
The editor only adds the bridge to a GameObject if its script has a save attribute or implements ISavable. Add one of the two for the bridge to appear.

Save, reload and autosave 0 no code 1 daily code#

Try it in the sample
Open sample 02: Buttons With No Code →

Sample 02 · Buttons With No Code

  1. Open the Buttons With No Code scene and press Play.
  2. Press the Save and Reload buttons and watch the Console.

Game code calls SaveActions. There is no Load call: a script gets its data when it registers.

A save file on disk holds data for objects that aren't loaded right now too, such as a boss in another scene: saving one file never touches data for objects outside it.

Destroying a GameObject (or one of its saved scripts) without calling Forget first leaves its last saved values on disk untouched. The next time something tries to capture its data, there's no live object left to read, so the save system logs that and keeps what was already saved instead of overwriting it with nothing. To make the data actually go away, call Forget before destroying it, as the samples do.

For buttons and UnityEvents, add MonoSaveActions instead of writing this code. The config's autosave checkboxes can save on quit, on focus loss, when a scene unloads, or every few minutes; all are off by default.

If it goes wrong
SaveAll writes nothing
Nothing changed since the last save. SaveAll only writes a file that changed.
SaveEventBus.OnSaveFailed fires
See React to loads and saves. The previous good file stays on disk.

Rename without losing data 1 daily code#

A saved field's name is part of its save data, so renaming a field can lose data. Formerly keeps it, on a MonoBehaviour exactly as on any other saved class:

A class's automatic save ID is its class name, so renaming the class can lose data too, unless it has [SaveId]. This only matters for a class registered with SaveActions.Register, a plain class or an ISavable one: both kinds work the same way.

A MonoBehaviour placed in a scene never needs [SaveId]. Its save ID comes from its Savable Bridge, not its class name, so renaming the class changes nothing.

React after a restore: IOnRestored 1 daily code#

Implement IOnRestored to run code right after your saved object's data comes back. Its OnRestored() runs after every restore: after Awake, when new-game values apply, and when a different game profile opens.

SaveTransform and SaveActiveState both use OnRestored this way: the fields hold the saved numbers, and OnRestored is where those numbers reach the GameObject.

An exception in OnRestored is logged, not thrown. The save system catches it, logs the saved object's type and save ID, and keeps the data it already restored. The rest of the restore continues.
If it goes wrong
OnRestored runs with fields still at their new-game values
A field without [Save] never gets restored. Check the field has the attribute.
An error names your type and "OnRestored... failed"
Your OnRestored threw. Fix the exception. The saved data underneath it is still intact.

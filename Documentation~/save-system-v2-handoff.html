Save System handoff: v1, v2, and v2 after review

What changed in three stages: the save system the shipped game uses (v1), the first v2 (steps 1 and 2), and v2 after your review (phase B). Each change shows the code in all three. How the system works today is on the main page, save-system.html.

v1

Tag save-system-v1. The shipped game stays on it.

  • A SaveManager in the boot scene.
  • Data restored at the end of the frame after a scene group loaded.
  • Only MonoBehaviours with a Savable Bridge could save.
  • Game profile listing and deleting were broken.

v2, steps 1 and 2

Commits T0 to T13.

  • Safe storage: atomic writes, a backup beside every file.
  • Restore after Awake and before Start.
  • No manager in the scene. Plain classes and assets can save.
  • Renamed the main class to SaveSystem; dropped the load events.

v2 after review

Commits A2 to B9, this run.

  • Names match the rest of the library again: SaveActions, SaveEventBus.
  • Save files are classes, so a typo doesn't compile.
  • Sticky load events, game profile handles, optional backups.
  • SaveStorage for tools, and a Create Config menu item.

// The class SaveSystem sat in the namespace

// code had to write SaveSystem.SaveSystem.

Back to the v1 names, which match SettingsActions and the rest of the library, and which no longer clash with the namespace (B1).

Picking a save file

v1
[Savable(SaveCategory.Game)]
public class Health : MonoBehaviour,
    ISavable<int> { … }

// SaveCategory: an enum edited by hand.
v2, steps 1 and 2
[Savable(SaveCategory.Game)]
public class Health : MonoBehaviour,
    ISavable<int> { … }

// Unchanged. The config's location field
// added Scene.
v2 after review
public class Health : MonoBehaviour,
    ISavable<int> { … }       // built-in GameProfile file

public class Chest : MonoBehaviour,
    ISavable<bool, SaveFiles.Scene> { … }

// SaveFiles.cs is written from the config's
// save file list. No attribute, no enum.

The config's save file list is the one place save files are defined. A library module ships its own save file class with [SaveFileDefaults], and the editor adds its row (B2).

When a script gets its data

v1
void Start()
{
    Current = 100;
    // Saved data arrives later, at the end of
    // the frame after the scene group loads.
}
// UI waited for OnLoadCategoryCompleted.
v2, steps 1 and 2
void Awake() { Current = 100; }
// Restored after every Awake and before any
// Start, so Start sees the saved value.
// No load events at all.
v2 after review
void Awake() { Current = 100; }
// Same timing. Load events are back for
// scripts that need "everything is ready":
SaveEventBus.OnLoadAllCompleted += Refresh;

Saving and loading

v1
SaveActions.SaveDataOf(SaveCategory.Settings);
SaveActions.SaveDataOfScope(SaveScope.Global);
SaveActions.LoadAll();
SaveActions.LoadDataOf(SaveCategory.Settings);
v2, steps 1 and 2
SaveSystem.Save("Settings");   // a string
// No load calls: objects restore when they
// register.
v2 after review
SaveActions.Save<SaveFiles.Settings>();
SaveActions.Reload<SaveFiles.Settings>();
// Reload: read the file from disk again and
// restore every object in it.

// MonoSaveActions: a dropdown picks the file.

Saving one file takes its class, not a string (B3). Saving never erases objects that aren't loaded, since step 1.

Game profiles

v1
SaveProfileManager profiles =
    SaveManager.Instance.ProfileManager;
profiles.CreateNewActiveProfileDirectory();
string[] ids = profiles.GetAllProfileIds();
// always empty
profiles.DeleteProfileDirectory(id);
// missed the folder
v2, steps 1 and 2
string id = SaveSystem.GameProfiles
    .CreateNew("Game Profile 2");
SaveSystem.GameProfiles.Open(id);
foreach (GameProfileManifest slot in
    SaveSystem.GameProfiles.GetAll()) { }
SaveSystem.GameProfiles.Delete(id);
// Works, but game code handles ID strings.
v2 after review
GameProfile created =
    SaveActions.GameProfiles.CreateNew();
GameProfile slot =
    SaveActions.GameProfiles.Get(2);
slot.Open();
foreach (GameProfile profile in
    SaveActions.GameProfiles.All) { }
slot.Delete();
// No IDs. Slot numbers never change.

A new game profile is named from the config ("Game Profile 3"). SaveActions.GameProfiles is never null (B5).

Events

v1
OnSaveAllCompleted
OnSaveCategoryCompleted(category)
OnSaveScopeCompleted(scope)
OnLoadAllCompleted
OnLoadCategoryCompleted(category)
OnLoadScopeCompleted(scope)
// A late subscriber missed the event.
v2, steps 1 and 2
SaveSystem.Saved
SaveSystem.GameProfileOpened(id)
// Load events removed: objects restore
// when they register.
v2 after review
SaveEventBus.OnLoadCompleted(Type)   // sticky
SaveEventBus.OnLoadAllCompleted      // sticky
SaveEventBus.OnGameProfileOpened(GameProfile) // sticky
SaveEventBus.OnSaveCompleted(Type)
SaveEventBus.OnSaveAllCompleted

Sticky means a script that subscribes after the event happened is called right away. A Scene save file raises its load event once per scene, one frame after that scene's scripts start. One throwing handler can't stop the others (B4).

Writing a file from a tool

v1
SavePathGenerator.Initialize(config);
string path = SavePathGenerator
    .GetPath(definition, profileId);
new FileDataStorageService()
    .SaveFile(json, path);
// Deleted the old file, then moved the new
// one in. A crash between lost the save.
v2, steps 1 and 2
var storage = new DiskStorageService(
    config.UseDebugPath, config.PrimaryFileExtension);
var store = new SaveFileStore(storage,
    new JsonSerializer());
string key = new SavePathGenerator().GetSaveFileKey(
    row.FileName, row.Location, null, null);
store.Write(key, saveFile);
// Safe, but five objects to write one file.
v2 after review
SaveStorage.WriteText<SaveFiles.Settings>(json);
SaveStorage.ReadText<SaveFiles.Scene>(
    profile, "Forest", out string json);
string path =
    SaveStorage.GetFilePath<SaveFiles.Settings>();
// The config says everything else. Works in
// edit mode. The storage parts are internal.

The Settings module's debug toolbar moved onto SaveStorage (B7).

Backup is a box on each save file row. The manifest and save system metadata are always backed up. A row with Backup unticked never falls back, and a corrupt file logs one error that names it. Deleting a game profile deletes its backups (B6). v2 doesn't read v1 save files.

What was checked

  • 178 EditMode and 13 PlayMode tests pass, in the Unity 7 Lab.
  • Every library module compiles in the Lab.
  • All six samples and a Settings scene were played in the Lab Editor, pressing their buttons: values survive save and reload, chests stay per scene, coins follow the game profile, slots open by number, a Settings change survives a new play session. No console errors.
  • Unity 6: the APIs the library uses were checked against the Unity 6 Scripting API. One Unity 7 rename (the searchable dropdown) now uses a version define. The tests have not been run in a Unity 6 project.

Decisions made during the run

  • Scene load events wait one frame. Unity runs each script's Start just before that script's first update, so in a scene's first frame some scripts haven't started. A hidden object in each loaded scene reports it ready one frame later. Restoring data never waits.
  • Backup unticked removes an old backup when the file is next written, so a stale backup can't load by surprise if the box is ticked again.
  • Only DiskStorageService takes the config. MemoryStorageService and SavePathGenerator read no config values, so they don't take it.
  • SaveStorage in play mode goes through the running save system's storage, which doesn't see the write. Call Reload<TFile>() after WriteText.
  • Samples ship their own save file classes, like a library module, because a sample's assembly can't see the game's SaveFiles.cs.
  • The main page was kept and rewritten as the save system's documentation (save-system.html), instead of being deleted as the plan said.

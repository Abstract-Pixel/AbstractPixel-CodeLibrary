What changed in the save system

Three versions side by side. v1 is what the shipped game uses. "v2 first" is steps 1 and 2. "v2 now" is today, after both of your reviews, the cleanup and phase S. The calls that changed since your second review are in their own section, phase S has its own, before and after, and the inspector fixes from your phase T feedback have theirs. How the system works today is in save-system.html, and what comes next is in save-system-v2-plan.html.

v1

Tag save-system-v1. The shipped game stays on it.

  • Needed a SaveManager in the scene.
  • Data arrived late, after Start.
  • Only MonoBehaviours could save.
  • Listing and deleting game profiles didn't work.

v2 first

Commits T0 to T13.

  • Safe saving, with a backup of every file.
  • Data arrives before Start.
  • No manager. Plain classes and assets can save.
  • Main class renamed to SaveSystem. Load events removed.

v2 now

Commits A2 to S9.

  • Old names back: SaveActions, SaveEventBus.
  • Save files are classes, and five built-in ones ship with the library.
  • Load events back, game profile objects, optional backups, save IDs you never type.
  • SaveStorage for tools. A Create Config menu item.
  • Autocomplete shows only what game code uses.
  • [Save] on a field, and mistakes that block play mode. Ready-made savers and UnityEvents for designers.

The main class

v1

v2 first
SaveSystem.SaveAll();
// Clashed with the namespace

v2 now
SaveActions.SaveAll();

The v1 name is back. It matches SettingsActions and has no clash.

Choosing a save file

v1
[Savable(SaveCategory.Game)]
public class Health : MonoBehaviour,
    ISavable<int> { … }
v2 first
[Savable(SaveCategory.Game)]
public class Health : MonoBehaviour,
    ISavable<int> { … }
// Same as v1.
v2 now
public class Chest : MonoBehaviour,
    ISaveIn<SaveFiles.Scene>
{
    [Save] bool isOpen;
}
// No attribute, no enum, no methods.

The five built-in save files ship with the library in SaveFiles. The editor writes your own rows from the config into GameSaveFiles.cs.

Phase S: saved fields and the ladder

S1 to S10, 13 and 14 Nov 2026. "Before" is the branch after phase K.

A saved field is one word (S1, S3)

Before
public class Health : MonoBehaviour, ISavable<int>
{
    public int Current { get; private set; }
    void Awake() { Current = 100; }
    public int CaptureData() => Current;
    public void RestoreData(int data) => Current = data;
}
Now
public class Health : MonoBehaviour
{
    [Save] int current = 100;
}
// A plain class adds SaveActions.Register(this).

Data is stored by field name. [Save(Formerly = "hp")] and [SaveId("Inventory")] keep data through renames. A script moved from ISavable<int> to one [Save] field keeps its saved value.

The wrong way is blocked (S2)

Before
[Save] GameObject target;
// Nothing existed to stop it.
Now
[Save] GameObject target;
// One error naming Health.target and the fix.
// Play mode won't start; the build fails.

Spawned copies (S5)

Before
Instantiate(goblinPrefab);
// Every copy shared one save ID.
Now
Goblin goblin = Instantiate(goblinPrefab);
goblin.SetSaveId($"goblin-{spawnPoint.name}");

Listening for one file (S6) and a failed save (S7)

Before
SaveEventBus.OnLoadCompleted += file =>
{
    if (file == typeof(GameSaveFiles.Ghosts)) ShowGhosts();
};
// A failed save raised nothing.
Now
SaveEventBus.AddLoadListener<GameSaveFiles.Ghosts>(ShowGhosts);
SaveEventBus.OnSaveFailed += (file, reason) => ShowError(reason);

For designers (S7, S8)

  • Save Transform, Save Active State and Save Destroyed components save position, on or off, and "picked up" with no code.
  • MonoSaveActions has On Loaded, On Saved, On Save Failed and On Game Profile Opened events, plus Reload Chosen File, Open Slot and New Game.
  • The config saves on scene unload and every N minutes if asked.
  • The Savable Bridge inspector lists each saved script's save file and fields, with a Copy save ID button.
  • A Continue button needs SaveActions.GameProfiles.LastOpened and Count.

Phase T so far: inspector fixes

15 Nov 2026. T1 (the bridge inspector cards) and T6 (the config inspector) had already landed; this was a run of fixes against your feedback on both, not a new phase T task. A later run on the same day finished T2, T5 and most of T4; see "T2, T4 and T5" at the end of this section.

Each saved field's type, at a glance (T1)

Before
current (int)
isPoisoned (bool)
Now
// Each name sits in a small badge with a colour dot for its type:
// blue for numbers, red for bool, amber for string, teal for enum...
current (int)
isPoisoned (bool)

The colours match Unity's own muted palette, not a bright accent colour, so the card still looks native. The save ID row now sits inside the card's own fold, so it hides when you collapse the card instead of staying on screen.

A new save file row stopped clashing with the one before it (T6)

Before
// Press "+" after the "Input" row, then rename it "Ghosts".
// The new row kept Input's class and storage name.
// It clashed with Input, and Update save file classes never appeared.
Now
// Press "+". The new row's class, storage name and built-in flag
// are blanked the instant it's added, before you type a name.
// Rename it "Ghosts": no clash, and the button appears.

Unity's own array insert duplicates the row before it, including fields the row's own inspector doesn't show. A new row looked identical to its neighbour until you renamed it, and renaming never changed its hidden class and storage identity. The list now resets those fields when a row is added, the same way a brand new row is built in code.

Still broken: removing a row

After the fix above, adding a row and renaming it correctly shows the Update save file classes button. Removing a row does not bring the button back, and I haven't reproduced this myself. capture editor_window crashed the Lab Editor three times trying to film the whole add-update-remove-update walkthrough you asked for, and I stopped using it rather than risk a fourth crash. The progress report has what's ruled out so far and a hypothesis to check first. SaveSystemConfigEditorTests only checks the button at the moment the inspector opens, never after a row is added or removed through the live list, so there's no test guarding this in either direction.

Choices I made

  • A Scene file's load event waits one frame, so every script in the scene has started.
  • Unticking Backup deletes the old backup on the next save.
  • Samples use the built-in save files. Sample 04 also ships one class of its own, the way a library module does, because samples can't see your GameSaveFiles.cs.
  • The ScriptableObject sample stays, as 08, until step 4 makes assets register on their own.
  • I kept the main page and rewrote it as the guide, instead of deleting it.

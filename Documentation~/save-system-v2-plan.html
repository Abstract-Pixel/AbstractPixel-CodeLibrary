Where the save system is going, in the order you'd learn it: designers first, then daily code, then the deeper levels. How the system works today is in save-system.html.

How it should feel

Someone who has never seen the save system should be able to use it alone, without help from an AI. Three rules decide every change:

  • The daily workflow is tiny and obvious. About 90% of a game uses two names: [Save] and SaveActions.
  • Advanced features are found from there. Autocomplete shows only what game code needs. Each call's doc comment names the next step. Each error names the fix.
  • The wrong way is hard. A setup that works but is secretly wrong shouldn't be possible. If the editor can see the mistake, play mode won't start.

Level 0: for designers

Today a designer can save from a button with MonoSaveActions, but saving anything in a level needs code. These close that gap, roughly in the order they arrive.

Save Transform, Save Active State, Save Destroyed step 3

Drop one on an object to save where it is, whether it's on, or that it was picked up (uses the gone marker). Most level objects need nothing else. Moved earlier than step 7, because [Save] makes each one about 15 lines.

Autosave settings step 3

"Save when a scene unloads" and "Autosave every N minutes", next to Save On Quit in the config.

Save events as UnityEvents step 3

A component with On Loaded (pick a file), On Saved and On Game Profile Opened, plus Reload Chosen File, Open Slot N and New Game on MonoSaveActions. A "Saved!" popup and the main menu buttons with no code.

Saved fields in the inspector step 3

The bridge shows which fields are saved, which file they go to and the save ID, with a Copy save ID button. In play mode it shows live values.

Saved-variable assets step 4

SavedBool, SavedInt and SavedString assets such as "Has Red Key" or "Quest Stage", read and set from UnityEvents. The usual way to handle quest flags.

"Saved" badge in the Hierarchy step 5

Bridges are added while editing, never at play time, and every saved object shows a small badge.

The Save System window step 6

Setup, Save Files, Saved Objects, Saved Data and Live. See and reset what's saved without opening JSON files.

Save slot screen and thumbnails step 7

A UI Toolkit prefab with slots, New, Delete with a confirm step, and Rename, plus a small screenshot per slot. The manifest already has room for it.

Setting up a game, once these exist

  1. Save System window → Set up. One button makes the config and the folder, then shows a short checklist: autosave, save slot screen, save files.
  2. Save Files page. The five built-in files are already there and locked. Add your own rows, such as Ghosts.
  3. On each object, Add Component → a saver, or a script with [Save] fields. The bridge is added for you and the Hierarchy shows a badge.
  4. Main menu. Drop in the save slot screen, or wire New Game, Continue and Load Slot through UnityEvents.
  5. Test. The Live page shows what was saved, with Open save folder, Clear this game profile and Reset this object.

Level 1: daily code

Mark it, and it saves step 3

A whole saved script
public class Health : MonoBehaviour
{
    [Save] int current = 100;
    [Save] bool isPoisoned;
}

public class QuestLog
{
    [Save] List<string> completedQuests = new List<string>();

    public QuestLog() { SaveActions.Register(this); }   // save ID "QuestLog"
}
  • Saves numbers, text, bools, enums, Vector2, Vector3, Quaternion, Color, lists, arrays, dictionaries and your own [Serializable] classes.
  • Data is stored by field name. Adding or removing a field never breaks an old save.
  • Renaming a field keeps its data: [Save(Formerly = "hp")] int health;. Renaming a class keeps it with [SaveId("Inventory")].
  • New-game values come for free built. A new game profile gets the values the object had before anything was restored.

The one timing rule built

Saved values come back right after every Awake and before any Start. Set new-game values in Awake or in the field itself; read them in Start.

Saving and forgetting built

SaveActions
SaveActions.SaveAll();                  // or let autosave do it
SaveActions.Forget(gameObject);         // a picked-up coin stays gone

There is no Load call. An object gets its data as soon as both exist.

The wrong way is hard

After each compile, the editor checks every saved type. A mistake it can see logs one error naming the type, the field and the fix. It also stops play mode from starting and fails the build. step 3, with [Save]

Decisions

  1. Five built-in save files ship with the library: GameProfile, Scene, Settings, Input, Achievements. A game's own rows go in GameSaveFiles.
  2. Three save locations, never more: Global, Game Profile, Scene.
  3. Register(this) needs no save ID. A custom one is optional.
  4. Forget on a scene object writes a gone marker.
  5. A Scene file in SaveStorage always needs a SceneField; the system never guesses the scene.
  6. Backups are optional per save file, ticked by default.
  7. Clean up by deleting and de-duplicating, never by merging into longer files.
  8. Mistakes the editor can see block play mode and builds.
  9. Renames of fields, classes, rows and objects never lose saved data.
  10. The GitHub project shows features and bug fixes only.
  11. ProjectRallyShift stays on v1.

Not doing

IdeaWhy not
XML or other file formatsOnly JSON is written. The config's xml, bak and tmp options get hidden.
More save locationsThree keeps the system easy to learn.
Saving on a background threadFiles are small, and threads plus Unity objects bring hard bugs. Measure first if saving ever stutters.
Cloud saves, compressionPlatform-specific. The storage seam is ready when a game needs them.
Encryption, for nowParked in issue #21 until a game needs it.

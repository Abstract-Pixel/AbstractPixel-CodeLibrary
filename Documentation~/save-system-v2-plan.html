Words we use

These words are now in the library's glossary, Modules/SaveSystem/GLOSSARY.md. Code names, tooltips, docs and GitHub issues all use them.

Save location

One of exactly three places data can live: Global, Game Profile or Scene.

Instead of: scope, save path

Global

Belongs to the player's machine, not to a playthrough. Settings, input bindings. Every game profile shares it.

Game Profile

One playthrough, like "Game Profile 1", and the location for its data: player health, inventory, quests. This is the default location.

Instead of: game, profile, save slot

Scene

One scene inside one game profile. Opened chests in the Forest. Always sits inside a game profile.

Save file

A named file that lives in exactly one location. Each location has a built-in one with its own name.

Instead of: category

Game profile manifest

A game profile's summary for the save slot screen: name, last saved time, playtime, last scene.

Save system metadata

Facts about the save system as a whole, kept in Global. Today it records which game profile was opened most recently, so the game can reopen it at startup.

Saved object

Anything whose data gets saved: a MonoBehaviour, a plain C# class or a ScriptableObject.

Instead of: savable

Save ID

The name of one saved object's data inside a save file. The locker number.

Capture and restore

Capture reads data out of an object for saving. Restore puts saved data back in.

Three save locations

Today's two scopes, Global and GameProfile, stay with the same names. "Scene specific" stops being a checkbox and becomes the third location. Developers can add more save files inside a location, but they can never add a fourth location.

What a developer can and can't change

Can add a save file and pick which of the three locations it lives in.
Can choose the file type for the whole project, such as .json.
Can't add a location, choose a folder, or nest folders. The three locations and their folders are fixed.

Scene names come from Unity's scene manager by default. Picking scenes in settings uses SceneReference from AbstractPixel Core, which works at runtime, so the SceneManagement module isn't needed.

Learn it in levels

You only need level 1 to start. Each level adds one thing and works the same way as the level before it.

1

Mark the fields you want saved

most scripts stop here
public class Health : MonoBehaviour
{
    [Save] int current;
    [Save] bool isPoisoned;
}

That's the whole script. The data goes to the built-in GameProfile file of the open game profile. The editor adds a Savable Bridge when you add the script to a GameObject.

Works with numbers, text, true/false, Vector2, Vector3, Quaternion, Color, lists, arrays, dictionaries and your own [Serializable] classes.
Can't save a reference to a GameObject, script or asset. Save its save ID instead. If you rename a field, add Unity's [FormerlySerializedAs("oldName")] and old saves still load.
2

Choose where it goes

public class Chest : MonoBehaviour, ISaveIn<SaveFiles.Scene>      // this scene only
{
    [Save] bool isOpen;
}

public class AudioSettings : MonoBehaviour, ISaveIn<SaveFiles.Settings>   // a file in Global
{
    [Save] float musicVolume;
}

Put the save file's name inside the angle brackets. Use a built-in file (SaveFiles.Global, SaveFiles.GameProfile, SaveFiles.Scene) or one a designer added. The file already knows its location, so you never say the location separately.

3

Full control over what gets saved

public class Health : MonoBehaviour, ISavable<HealthData, SaveFiles.GameProfile>
{                                       //      what you save   where it goes
    public HealthData CaptureData() => new HealthData { current = current };
    public void RestoreData(HealthData data) => SetHealth(data.current);
}

Use this when you need logic, such as calling a method on restore instead of setting a field. It's today's ISavable<T> without the [Savable] attribute. The second part is optional. ISavable<HealthData> alone uses the GameProfile file.

4

Special cases

look these up when you need them

A plain C# class

public class Inventory
{
    [Save] List<string> items = new();

    public Inventory()
    {
        SaveSystem.Register(this, "player-inventory");
    }
}

A plain class has no GameObject to carry a save ID, so you name it yourself. If saved data exists, it gets restored right inside Register.

A ScriptableObject

public class GameProgress : ScriptableObject
{
    [Save] int chapter;
}

Same as level 1. The editor finds every asset with saved fields, and the save system registers it at game start.

Spawned copies

One line per copy. See Spawned copies.

Run code after restore

Add an OnRestored() method through a small optional interface, for example to refresh a health bar.

Game profiles

SaveSystem.GameProfiles.CreateNew("Game Profile 1"), Open, Delete, All.

Save from code or buttons

SaveSystem.SaveAll(), or MonoSaveActions for UnityEvents.

Timing, shown with one value

Take a Health script. A new game starts at 100 health. The player saved last session with 37 health. Each row follows the value of current through one scene load.

In v2

1 · Awake

current = maxHealth;

current = 100

The value for a brand new game.

2 · Save system restores

// done for you

current = 37

The saved value replaces the new-game value.

3 · Start

healthBar.Show(current);

Health bar shows 37. Correct.

Today

1 · Awake

current = 100

2 · Start

Health bar shows 100.

3 · End of frame, load runs

current = 37

The value is right, but the bar still says 100. So you add load events or change execution order to work around it.

The one mistake to avoid in v2

Start runs after the save system restores. So if your Start sets a saved field, it replaces the value the player saved. Here are the same two lines of code, written two ways.

Right: new-game value in Awake

void Awake() { current = maxHealth; }
void Start() { healthBar.Show(current); }
Awake100new-game value
Restore37saved value replaces it
Start37only reads it
The player continues with 37 health, as they left it.

Wrong: new-game value in Start

void Start()
{
    current = maxHealth;          // overwrites the save
    healthBar.Show(current);
}
Awake0nothing set yet
Restore37saved value arrives
Start37 100Start writes 100 on top
The player loads their save and has full health again. The next save writes 100, and the 37 is gone for good.

The code checker in the editor warns when a script assigns one of its saved fields inside Start, and points at the line.

The rule in two sentences

Awake answers "what are my values in a brand new game?". Start answers "now use my values". The save system restores between the two, so you never touch execution order.

This works because restoring happens as soon as both the object and its saved data exist, whichever is ready second. Saved data is normally read at game start, before any scene object exists. If the player opens a game profile later from a main menu, restoring happens at that moment instead, and OnRestored() lets you refresh things like the health bar.

Spawned copies

This only matters for objects your code creates while the game runs, with Instantiate. Objects you place in a scene in the editor already have their own save ID.

The problem

A prefab is a template. Every copy is identical, including its save ID. Three goblins share one ID, so each save overwrites the one before.

Next session, your spawner creates the goblins again with the same names, and each one gets its own data back. The save system doesn't create goblins. It only fills in their data.

Platforms

PC and Steam Deck today. Maybe Switch 2 and PS5 later. Storage and JSON already sit behind their own interfaces. One change makes consoles fit.

Today storage works with folders

It has CreateDirectory, GetDirectories and full paths built from Application.persistentDataPath. Console save APIs don't give you folders like that.

In v2 storage works with names

Storage only knows "save this text under GameProfiles/a1b2c3/GameProfile" and "give me the text for that name". DiskStorageService turns names into folders. A console version maps them to its own save slots.

What gets fixed

Saving erases the data of objects that aren't loaded right now, such as objects in another scene.

LoadedSaveData keeps that data.

Spawned copies share one save ID.

SetSaveId gives each copy its own.

The bridge gets added during play mode, where it stays empty, or at build time, where its ID changes every build.

The editor adds bridges while you edit and saves the IDs into the scene.

A crash mid-save can leave no save file at all.

The new file replaces the old one in one step, and the old one stays as a backup.

The list of game profiles is always empty, because the manifest is saved with ".json" and loaded without it.

SavePathGenerator builds every name, so save and load always match.

Deleting a game profile looks in the wrong folder.

Same fix.

Data restores too early or too late depending on execution order.

Restore between Awake and Start.

Calling a save method with no SaveManager in the scene creates an empty one, which crashes.

No scene object needed. SaveStartup loads the config.

Scene data crashes without SceneCoordinator.

UnitySceneInfo is the default.

"Delete All Save Files" deletes nothing. "Encrypt file" and "ignored scenes" do nothing.

Tools share the game's code. Unused settings get built or removed.

Decisions

Decided

  • The finished map is a v2 plan ready to build.
  • v2 is for future games and doesn't read the shipped game's saves.
  • Exactly three save locations: Global, Game Profile, Scene. Scene sits inside a game profile. Game Profile is the default.
  • Your original names stay: SavableBridge, SaveProfileManager, GameProfileManifest, SavePathGenerator, IDataStorageService, ISerializer, JsonSerializer. SaveScope becomes SaveLocation, SystemMetaData becomes SaveSystemMetaData.
  • Developers add save files, never locations or folders.
  • No [Savable] attribute. [Save] fields, or one interface that says what and where.
  • MonoBehaviours, plain C# classes, ScriptableObjects and spawned copies all save.
  • Timing: new-game values in Awake, restore before Start.
  • Scene names don't need the SceneManagement module.
  • Single player. Works for level-based, systems-based and open world games.
  • PC and Steam Deck now. Storage by name so consoles fit later.
  • Each game profile has a manifest for the save slot screen.
